AI Scan Review: requirements and architecture (v1)

This document gives the product contract, the architecture, and the targets for v1. We select the tools later (scanners, advisory sources, classifier, LLM). Each tool must agree with the criteria in section 7.

1. Problem and product principles

User needThe user asks two questions: “Am I exposed?” and “What do I fix first?”. The user wants a decision, not a dataset.
ProblemA scanner gives hundreds of duplicate rows with no context. The scanner sorts the rows by CVSS. Users stop reading the report, and nobody fixes the problems.
Root causeScanners report symptoms (vulnerability × package × dependency path), not causes. Severity is not the same as risk. No finding has a link to an action.
Product responseGroup the findings into root-cause Issues (problem, root cause, fix, evidence). Sort the Issues by real risk. Give the user an ordered action plan.
P1. Issues, not findingsShow Issues to the user. A finding is the evidence for an Issue.
P2. Rules decide, the LLM explainsRules and calibrated classifiers make the decisions. The LLM only explains them. You can switch off the LLM.
P3. Each report is reproducibleEach report shows its source: commit SHA, scanner version, advisory-data time, and what was scanned and not scanned.
P4. Degrade, do not failIf an optional part fails, the user receives a partial result. The report shows which part is missing.

2. Scope (v1)

In v1

  • Public GitHub repositories, by URL. Optional branch, tag, or SHA. The server must have a GitHub token.
  • Dependency scan for one ecosystem: the npm lockfile. Secret, CI/CD-configuration, and code scanners connect through the same adapter contract.
  • Asynchronous scans, live progress, a report screen, and a React UI.
  • The system runs in containers. One command starts it on a local computer.

Not in v1 (next steps)

  • Authentication and multi-tenancy
  • Private repositories, and repository connection through a GitHub App
  • Rescans from pull requests, and differences between two scans
  • Pull requests that apply fixes automatically
  • Reachability analysis
  • Other ecosystems

3. Functional requirements

IDRequirementAcceptance criteria
FR1Submit a scanThe system accepts github.com/{owner}/{repo}, the .git form, and the /tree/{ref} form. It does all checks before it puts the scan in the queue. URL not correct → 400 INVALID_URL. Repository missing or private → 404 REPO_NOT_FOUND. Repository too large → 422 REPO_TOO_LARGE.
FR2Idempotent submitThe client can send an Idempotency-Key header. Same key and same body → the system sends the first response again. Same key and a different body → 422. First request still in progress → 409. The system keeps each key for 24 h.
FR3One scan for each commitMaximum 1 active scan for each (repository, commit SHA, scanner version). The system uses a completed result again if it is less than 24 h old. Send force=true to scan again. The response shows deduplicated or cached.
FR4Lifecyclequeued → running(stage) → completed | failed | cancelled. A partial result is completed, and the report lists the coverage gaps. Each accepted scan always gets to a terminal state.
FR5Follow the progressGET gives a snapshot. SSE gives a live stream. After a disconnection, the stream continues from Last-Event-ID. The user sees the stage, the percentage, the queue position, and a timeline in plain words.
FR6CancelPOST /scans/:id/cancel. The scan must change to cancelled in 10 s or less.
FR7Scanner adaptersAll scanners use one adapter contract. Input: the workspace and the repository context. Output: normalized findings. Each adapter declares its category, timeout, and resource class. v1 has the dependency category.
FR8Normalize and mergeEach finding has a stable ID: a hash of type, advisory, package@version, and location. The system merges duplicate advisory IDs for one issue, for example a CVE and its GHSA.
FR9Exploit dataEach vulnerability shows a known-exploited flag, an exploit-probability score, fix available (yes or no), and the fixed version.
FR10Context classification (optional)A classifier makes fuzzy decisions with confidence thresholds: file role, real or placeholder secret, repository type, impact class. Without the classifier, rules make these decisions. A suppressed finding stays visible, and the user can restore it.
FR11Issues and priorityEach Issue has a problem, a root cause, a fix (command, target version, effort), and evidence. A transitive vulnerability belongs to the direct dependency that brings it in. A fixed scoring formula sets the priority.
FR12ReportVerdict (risk level and headline), the top Issues (5 or fewer), an ordered action plan, statistics, coverage (scanned, not scanned, and why), and provenance.
FR13AI explanation (optional)The output must agree with a schema. Each claim must refer to an Issue ID or a finding ID. If the AI fails or is too slow, the system uses template text. The report shows the label “AI-generated”.
FR14Browse findingsPages of 100 findings or fewer. Filters: severity, category, prod or dev, suppressed.
FR15Typed errorsEach error has {code, message, retryable}. A repository with nothing to scan is completed with a coverage note. It is not an error.
FR16Web UIReact: submit → live progress → report. The link ?scan={id} works after a page refresh.

Invariants

Each invariant must be true 100% of the time. Each invariant has an automated test.

  1. Each accepted scan gets to a terminal state.
  2. Maximum 1 active scan for each scan key. Same idempotency key and same body → same scan ID.
  3. The system does not lose or duplicate a progress event when a client connects again.
  4. AI output never changes the severity, the priority, the fix command, or the version. The system shows these values from data.
  5. The system never stores, returns, or logs a raw secret value.
  6. Same commit + same scanner version + same advisory snapshot → the same findings, Issues, and ranking.

5.8 Security

  • No execution. Never install, build, or run repository code.
  • One sandbox for each scan. No credentials. Resource limits from 5.6. Outbound traffic only to an allowlist.
  • No SSRF. The system makes outbound URLs only from the parsed owner and repository name. It never uses the raw user input as a URL.
  • Secrets. The adapter redacts secret values at its boundary.
  • LLM input. Repository text goes to the LLM only as structured fields with length limits, after a prompt-injection screen.
  • Credentials. Read them only from environment variables or a secret store. Never log them or return them.

Tool decisions for later

Each candidate tool must satisfy all criteria in its box.

Scanner adapters

  • The license allows commercial SaaS use.
  • It never runs repository code.
  • Machine-readable output.
  • ≤ 45 s p95 and ≤ 1 GB on M-class repositories.

Advisory and exploit-intel sources

  • The terms allow commercial use.
  • Refresh at least each day.
  • Batch lookups.

Classifier

  • Typed outputs with calibrated confidence.
  • ≤ 0.5 s p95.
  • ≤ $0.001 per scan.

LLM

  • JSON-schema output.
  • ≤ 20 s p95 for ~1k output tokens.
  • ≥ 150k tokens/min.
  • ≤ $0.01 per scan.

Notes

  • The capacity numbers come from the assumptions A1 to A8. The most important assumptions are the 45 s mean scan time and 0.5 vCPU / 1 GB for each scan.
  • The queue model supposes more regular scan times than real repositories have. Thus, the real tail wait times are probably longer than these values.
  • After the first load test, replace the assumptions and the model values with measured values.
  • The 3-hour build covers a part of this design: one host and one scanner category. In the presentation, show these values as design targets, with the measured results next to them.

Glossary

Finding
One raw result from a scanner, for example one vulnerability in one package version.
Issue
A group of findings with one root cause and one fix.
Design point (DP)
The peak load that the design must carry: 1,000 scans/h.
p50, p95, p99
50, 95, or 99 of 100 measurements are at this value or less.
Slot
The capacity for one scan on a worker host: maximum 1 vCPU, 1 GB RAM, and 2 GB disk.
W (service time)
The mean time that one scan uses a slot: 45 s.
ρ (utilization)
The part of the slots that is in use. 0.6 = 60%.
Erlang C (M/M/c)
A standard queue model. It calculates the queue wait from the number of slots (c), W, and ρ.
Little's law
Mean number of scans in the system = arrival rate × mean time in the system.
RPS
Requests per second.
Idempotency key
A unique value from the client. The server uses it to find a repeated request.
Scan key
(repository, commit SHA, scanner version). Maximum 1 active scan for each scan key.
Lease and heartbeat
A worker holds a scan for 30 s. It extends the lease each 10 s. If the lease expires, another worker can claim the scan.
SKIP LOCKED
A PostgreSQL option. Each worker claims a different row, and no worker waits for another worker.
SSE
Server-sent events: a one-direction HTTP stream from the server to the browser. The browser connects again automatically and sends Last-Event-ID.
Load shedding
The API refuses new scans (503) when the queue is too long.
Fallback
A simpler method that the system uses when an optional part fails, for example template text instead of AI text.
RPO
Recovery point objective: the maximum data loss after a failure. Here: 0.
LCP, INP, CLS
Core Web Vitals: load time of the largest content, response time to user input, and visual stability.
